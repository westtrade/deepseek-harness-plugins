# `dsh-cron-schedule`

Планировщик задач для DeepSeek Harness: **в заданное время создаётся новый чат
в выбранном каталоге и получает задачу для ИИ**. Есть панель управления в
веб-интерфейсе и инструменты, которыми ИИ сам может завести расписание.

## Что делает

- **Два текста вместо одного.** У задачи два поля:
  **Setup brief** («промпт при инициализации», необязательный) — большой
  инструктаж: кто бот, где доска, как работать; и **Task on every run**
  (обязательное) — короткая задача на каждый запуск.

  | Куда попадёт | Что отправится |
  |---|---|
  | новый чат (первый запуск задачи, или любой запуск с «always new chat») | сначала **brief**, отдельным сообщением, затем **задача** |
  | тот же чат (следующие запуски) | только **задача** |

  Так 2000-токенный инструктаж читается один раз, а не повторяется каждые 30
  минут. Пустой brief = прежнее поведение (одна задача). Очистить уже
  сохранённый brief можно, стерев поле и сохранив задачу; чтобы применить новый
  brief к существующему чату, начните переписку заново — выберите в выпадайке
  чата «First run creates a chat…» (привязка снимется) или включите
  «always new chat».

- **Страница управления расписаниями** — открывается по строке **«AI schedules»**
  в сайдбаре (с иконкой часов). Таблица задач: имя, расписание, следующий
  запуск, каталог, действия. У каждой задачи кнопки
  **Run now / Edit / Disable / Delete**; **Edit** разворачивает редактор прямо
  под строкой — форма та же, что при добавлении, с уже заполненными полями,
  кнопками **Save changes** и **Cancel** (отмена ничего не сохраняет).
  Каталог выбирается **селектором из сохранённых workspace или файлпикером
  ОС**, есть поле задачи для ИИ и живой предпросмотр ближайших запусков по мере
  ввода выражения.
- **Расписание**: пресеты в интерфейсе (каждый час, каждые 30 минут, ежедневно
  в 09:00, по будням, по понедельникам, 1-го числа) **или** произвольное
  cron-выражение.
- **Чат задачи** — куда попадает сообщение при срабатывании:

  | Настройка | Поведение |
  |---|---|
  | чат **не указан** | первый запуск создаёт чат в каталоге задачи и **привязывает его к задаче**; все следующие запуски пишут в него же, так что повторяющаяся задача ведёт одну переписку |
  | чат **указан** в выпадайке | используется всегда именно он |
  | галка **«Always start a new chat»** | каждый запуск создаёт **новый** чат, привязка не устанавливается (и стирается, если была) |

  Галка снимается — и следующий запуск снова привязывает чат. Состояние видно в
  таблице, в колонке **Chat**: название чата, «not yet created» или «new each
  run». В выпадайке — существующие чаты с их названиями, как в сайдбаре.

  **Run now сразу открывает чат этого запуска.** Кнопка создаёт (или
  переиспользует) чат, ждёт, пока запуск действительно отправит в него задачу, и
  только потом переключает браузер на этот чат — панель расписаний при этом
  закрывается, как при выборе чата в сайдбаре. Чат берётся из ответа самого
  маршрута (`lastSessionId`), то есть это ровно тот чат, куда попало сообщение:
  новый для галки «always new chat», привязанный в остальных случаях. Упавший
  запуск никуда не уводит — в строке остаётся текст ошибки. То же поведение у
  кнопки **Run** в баннере пропущенных запусков.

  **Список чатов фильтруется по выбранному каталогу**: чат принадлежит той
  папке, где он создан, поэтому в выпадайке видны только чаты этой папки.
  Смена каталога сбрасывает выбранный чат — задача не может писать в чат
  чужого проекта. Пока список грузится, рядом с селектором видно
  «Loading chats…» со спиннером — иначе при смене каталога выпадайка просто
  выглядит пустой. **Пустые, архивные и субагентские чаты в списке не
  показываются**: пустой чат человек не использовал и опознать его нечем,
  архивный он убрал сам, а субагентский принадлежит делегированию родительского
  запуска, и расписание не должно в него писать. Форк-чаты (у которых тоже есть
  родитель) остаются — это обычные чаты.
  **Название чата берётся из его заголовка, а если заголовка нет — из первого
  сообщения человека**, поэтому в списке не бывает строк из одного пути.
- **Запуск**: в момент срабатывания сообщение уходит в чат задачи. Чат
  появляется в общем списке сессий как обычный — со своей моделью, правами и
  пресетом; созданный задачей помечен `source.kind: "cron"`, а при
  переиспользовании сообщение добавляется через тот же путь, что и обычная
  отправка из веб-интерфейса (закрытый чат при этом возобновляется).
- **Пропущенные запуски**: если DSH был выключен, по умолчанию ничего не
  догоняется — панель показывает баннер «столько-то запусков пропущено» со
  списком времён и кнопками **Выполнить** и **Пропустить**.
- **Галочка «Catch up missed runs after a restart»** (только для человека):

  | Галочка | Поведение при следующем запуске DSH |
  |---|---|
  | **нажата** | задача догоняется сразу сама: пропущенный запуск выполняется, создаётся чат, список пропущенных очищается |
  | **не нажата** | задача ждёт разрешения: пропущенные копятся и показываются в баннере с кнопкой «Выполнить» |

  Состояние видно в таблице (колонка **Catch-up**: `auto` / `ask`), а в
  редакторе галочка уже проставлена так, как сохранено. **ИИ не может её
  поставить** — см. ниже.
- **Модель у задачи**: в редакторе есть выпадайка — конкретная модель или
  «Deployment default» (тогда задача следует за моделью по умолчанию, и её
  смена подхватывается). Выбранная модель видна в таблице, в колонке **Model**,
  и применяется к чату, который создаёт задача.
- **Список допустимых моделей** — карточка **«Models the AI may schedule on»**
  на странице **Settings → Plugins → Plugin Configuration**, оформленная так же,
  как карточка Subagent: сворачиваемая строка с названием и описанием, внутри —
  каталог моделей **галочками, сгруппированный по провайдерам**, и кнопки
  **Save / Discard** (правки копятся до сохранения, несохранённое помечается
  меткой «Unsaved»). Плагин публикует её как собственный namespace настроек
  (`cron-schedule`), поэтому значение хранится штатным сервисом настроек, а не
  только в файле плагина. Пустой список = без ограничений: и панель, и ИИ видят
  весь каталог. Стоит добавить хотя бы одну запись — и выпадайка в панели, и
  `cron_create` у ИИ ограничиваются только этим списком. Изменять список может
  **только человек** (та же защита, что у галочки авто-догона).
- **Модель по умолчанию** для задачи без своего выбора — **последняя
  использованная в чатах** (та же, что показывает селектор в композере).
  Модель развёртывания берётся только как крайний случай, поэтому в селекторе
  больше нет строки «Deployment default».

### Инструменты для ИИ (model-facing tools)

| Инструмент | Назначение |
|---|---|
| `cron_list` | список расписаний с id, состоянием, описанием и следующим запуском |
| `cron_create` | создать расписание; `sessionId` — чат для переиспользования, `alwaysNewChat` — новый чат на каждый запуск, `model` — из `cron_models` |
| `cron_chats` | какие чаты существуют, чтобы указать конкретный |
| `cron_models` | какие модели ИИ разрешено указывать (и какая модель по умолчанию) |
| `cron_describe` | объяснить выражение и показать ближайшие запуски, ничего не сохраняя |
| `cron_run` | запустить расписание немедленно, не сдвигая график; в ответе — `sessionId` чата запуска и итог (`lastStatus`) |
| `cron_delete` | удалить расписание по id (или по уникальному имени) |

`cron_run` и `cron_delete` принимают **id или точное имя** задачи: имя
неоднозначно — инструмент честно отказывается и перечисляет id, вместо того
чтобы удалить не то расписание.

#### Как тулы попадают к агенту

Плагин регистрирует их штатно — `ctx.tools.register()` из
`@deepseek-ai/dsh-tools`, — и они появляются в **списке инструментов каждой
новой сессии** рядом со стандартными, без системного промпта и без
«включения»: достаточно, чтобы плагин был в профиле. Сессия, открытая *до*
установки/перезагрузки плагина, набора не увидит — начните новый чат.

Ответ агента «инструментов не было» почти всегда значит одно: **все семь
регистраций упали на валидации схемы**, и модель не получила ничего.

- `output.schema` живёт в **урезанном JSON-Schema** харнесса: `required` —
  это **массив имён свойств на объекте**, а не `required: true` внутри
  свойства; при `additionalProperties: false` схема обязана перечислять ровно
  те ключи, которые вернул `execute`.
- каждая регистрация обёрнута в `try/catch`: один плохой инструмент стоит
  одного инструмента, а не всех семи, и в лог хоста уходит
  `cron-schedule: tool "cron_…" was not registered: …`.
- `scripts/host-test.mjs` держит зеркало этих правил и проверяет значения
  всех семи тулов против их схем, поэтому такое молчание больше не пройдёт
  незамеченным.

Как агент узнаёт о плагине, если тулов в его сессии нет (старый чат,
headless-композиция, доступ только по HTTP) — **один запрос**:

```sh
curl -s http://127.0.0.1:3080/api/cron-schedule/manifest | jq
```

`GET /api/cron-schedule/manifest` (только чтение, доверенная сессия не нужна)
отдаёт: список инструментов с их живыми описаниями, поля задачи с типами и
ограничениями, все HTTP-маршруты с пометкой `humanOnly` и значения
`lastStatus`. Файлы плагина читать не нужно.

#### Agent quick-start

> Планировщик задач: `cron_list` (что уже есть), `cron_models` (какие модели
> можно указывать), `cron_describe` (проверить выражение заранее),
> `cron_create` (создать), `cron_run` (запустить сейчас), `cron_delete`
> (удалить), `cron_chats` (только если нужен конкретный существующий чат).
> Минимум для «каждые 30 минут в этой папке»:
> `cron_create({ name: "Half hourly", expression: "*/30 * * * *",
> workspacePath: <абсолютный путь>, prompt: <что делать> })` — `workspacePath`
> можно не указывать, тогда берётся папка текущего чата. Если у бота есть
> большой постоянный инструктаж, положите его в `initialPrompt`: он уйдёт один
> раз в новый чат, а `prompt` останется короткой задачей. Проверка —
> `cron_list`: у задачи `nextRunAt` в будущем. Немедленный запуск —
> `cron_run({ id })`; ответ содержит `sessionId` чата, куда ушла задача.
> Ошибки приходят как `{ error, field }`, где `field` — имя поля.

## Установка

```sh
git clone https://github.com/westtrade/deepseek-harness-plugins ~/deepseek-harness-plugins

mkdir -p ~/.dsh/profiles/node_modules
ln -sfn ~/deepseek-harness-plugins/dsh-cron-schedule \
        ~/.dsh/profiles/node_modules/dsh-cron-schedule
```

Затем добавьте строку в слой патча профиля
(`~/.dsh/profiles/web/cordis.patch.yml`):

```yaml
- insert:
    - id: cron-schedule
      name: 'file:///home/USER/.dsh/profiles/node_modules/dsh-cron-schedule/lib/index.js?rev=1'
      config:
        locale: ru
```

Обновите страницу GUI. Без `patchReload: live` — перезапустите `dsh web`.

### Почему `file://` и `?rev=`

Загрузчик патча прогоняет **относительное или абсолютное** имя через
`pathToFileURL()`, а тот превращает `?` в `%3F` — файл «не найден», импорт
падает, и весь патч-релоад молча откатывается на прежнюю копию. Форма
`file://` под перезапись не попадает, поэтому query выживает, и **увеличение
`rev` перечитывает код без перезапуска сервера**. `lib/index.js` прокидывает
этот query и в свои импорты (`store.js`, `scheduler.js`, `runner.js`,
`cron.js`) — иначе перечитается только входной файл, а вложенные модули
останутся старыми.

## Как работает

- **Расписание** — свой cron-движок (`lib/cron.js`) без зависимостей: пять
  полей, диапазоны, списки, шаги, имена месяцев и дней, `@daily`-макросы,
  `0`/`7` = воскресенье и правило Vixie «день месяца ИЛИ день недели». Расчёт
  идёт по настенным часам выбранного пояса IANA, поэтому переход на летнее
  время не сдвигает задачу.
- **Планировщик** (`lib/scheduler.js`) держит **один** таймер на ближайшую
  задачу, пересчитывая время от настенных часов на каждом пробуждении. Задержка
  ограничена максимумом `setTimeout` (~24,8 суток) — задача на месяцы вперёд
  всё равно сработает.
- **Хранилище** (`lib/store.js`) — один JSON-файл `$DSH_HOME/cron-schedule.json`,
  запись через временный файл и `rename`, поэтому сбой не оставит
  полузаписанный список. Битый файл читается как пустой, а не роняет плагин.
- **Запуск** (`lib/runner.js`) повторяет путь кнопки «новый чат» в GUI:
  `workspaceRegistry.create` → `agents.create({meta: {cwd, agentPreset},
  agentOptions})` → `attachSession` → `followup(сообщение)`. Неудачный запуск
  откатывает созданную сессию, чтобы не осталось чата-призрака.

### Как галочка защищена от ИИ

Галочка авто-догона — единственная настройка, которую ИИ не может включить.
Защита стоит **на сервере**, а не в интерфейсе, потому что модель умеет
вызывать те же HTTP-маршруты через `bash`/`curl`:

1. **Хост спрашивает сервис `connection`** (`requestRejection(req)`) —
   тот самый, что охраняет `/api` в веб-профиле. Он применяет проверку
   Host/Origin и подписанную cookie, выданную при входе в GUI. `undefined` =
   запрос прошёл (человек в браузере); код 401/403 = не прошёл.
2. **Флаг принимается только от доверенного запроса.** Любой другой —
   инструмент ИИ, `curl` из shell-тула, скрипт, запрос из локальной сети —
   получает `400 autoCatchUp can only be changed by a person in the Web panel`.
3. **Инструмент `cron_create` вообще не имеет такого параметра**, и его
   обработчик явно удаляет поле из входных данных. Инструмента обновления у
   ИИ нет.
4. **Снять галочку можно всегда** — это безопасное действие, отказа в нём нет.
5. Если сервиса `connection` в композиции нет (headless-профиль), не доверяется
   никто, и галочку там поставить нельзя.

Итого: включить авто-догон может только человек, нажавший галочку в панели.

### Кто что может

Агент и человек видят один и тот же HTTP-интерфейс, кроме двух вещей, которые
по определению человеческие. Единственный признак «это человек» — доверенная
браузерная сессия из `connection.requestRejection` (cookie, выданный при входе,
плюс проверка Host/Origin). Своего тула у ИИ нет — ИИ идёт через `ctx.tools`,
а не через HTTP, но и там запрет продублирован.

| Что | Кто может | Как отказывает |
|---|---|---|
| `GET …/manifest`, `GET …/jobs`, `GET …/jobs/<id>`, `GET …/chats`, `GET …/settings` | кто угодно | — |
| `POST …/jobs`, `POST …/jobs/<id>`, `POST …/jobs/<id>/run`, `DELETE …/jobs/<id>`, `POST …/jobs/preview` | кто угодно | `400 { error, field }` на невалидных данных |
| поле `autoCatchUp` (авто-догон пропущенных запусков) | **только человек** | `400`, поле `autoCatchUp`; `cron_create` вырезает его молча |
| `POST …/settings` (список допустимых моделей) | **только человек** | `400`, поле `allowedModels` |
| `cron_*` инструменты | агент | вне allow-list модель отклоняется: `{ error, field }` |

### Что отвечает запуск

`POST …/jobs/<id>/run` (и инструмент `cron_run`) **синхронный**: ответ приходит
тогда, когда запуск уже отправлен в чат. Полезные поля ответа:

- `job.lastStatus` — `started` (идёт), `succeeded` (сообщение доставлено),
  `failed` (не дошло, причина в `job.lastError`);
- `job.lastSessionId` — **чат этого запуска**: новый, если у задачи включён
  «always new chat», иначе привязанный;
- `job.sessionId` — чат, привязанный к задаче навсегда (после первого успешного
  запуска; у задачи с `alwaysNewChat` его нет);
- `job.runs` / `job.missed` — история запусков и пропущенные времена (в таблице
  это колонка Chat и баннер пропусков).

Сообщения в чате помечены источником `source.kind = "cron"` и полем
`source.stage`: `init` — инструктаж (setup brief), `task` — обычная задача.
Поэтому в переписке видно, где бот получал инструктаж.

Инструмент `cron_run` повторяет главное в своём ответе (`started`, `id`,
`sessionId`, `lastStatus`, `lastError`), чтобы модели не понадобился второй
запрос `cron_list`.

### Шпаргалка: новый чат или тот же?

| Что настроено | Куда попадёт запуск |
|---|---|
| ничего не указано | 1-й запуск создаёт чат и привяжет его к задаче, следующие идут в него |
| `sessionId` из `cron_chats` | всегда в этот чат |
| `alwaysNewChat: true` | каждый запуск — новый чат, привязка не ставится |

С брифом (`initialPrompt`) правило то же, но в новый чат сначала уходит бриф,
затем задача. В уже существующий чат бриф не отправляется никогда — он там уже
есть (или его там не было: чат создан задачей до появления брифа).

`alwaysNewChat` включается из панели (в инструментах `cron_create` поле тоже
есть) и снимается обратно; после снятия следующий запуск снова привяжет чат.

### Как список моделей ограничивает ИИ

Список допустимых моделей — это политика, которая сужает выбор ИИ, поэтому
менять его тоже может только человек, и проверка стоит на сервере:

1. **`POST /api/cron-schedule/settings` требует доверенной сессии** — тот же
   `connection.requestRejection`, что и у галочки. ИИ, `curl` и скрипты
   получают `400`.
2. **Список проверяется на обоих путях создания задачи** — и в HTTP-маршруте,
   и в инструменте `cron_create`, так что обойти его через тул нельзя.
3. **Модель сверяется с каталогом развёртывания** (`ctx.llm.listProviders()` /
   `listModels()`). Задачу на несуществующую модель нельзя создать ни через
   панель, ни через `cron_create` — ошибка приходит сразу, а не при срабатывании.
4. **Сохранение списка не блокируется мёртвыми записями.** Панель всегда
   отправляет весь список, а нарисовать галочкой она может только модели из
   каталога: запись, которую провайдер убрал или переименовал, в карточке не
   видна, и снять её вручную нельзя. Поэтому `POST` от человека убирает такие
   записи сам и отвечает их списком в поле `dropped`, а карточка показывает
   это под формой — иначе список нельзя было бы сохранить вообще никогда.
   Записи провайдера, каталог которого **не удалось прочитать** (ошибка в
   `listModels`), при этом сохраняются как есть: случайный сбой провайдера не
   должен вычищать политику.
5. **ИИ видит границы сам**: `cron_models` возвращает `restricted` и ровно тот
   набор, из которого ему разрешено выбирать.
6. **Снять ограничение может только человек** — очистить список через
   `POST` тоже можно лишь из браузера.

### Как задача переиспользует чат

- **Привязка хранится в задаче** (`sessionId`). Её ставит либо первый запуск
  (чат создан задачей — он и запоминается), либо человек через выпадайку.
- **Закрытый чат не проблема**: сообщение уходит через
  `sessionController.prompt()`, который сам поднимает сохранённую сессию и
  возобновляет на ней агента. Поэтому переиспользование работает и после
  перезапуска DSH, а не только пока чат открыт.
- **Каждая отправка идемпотентна**: ей даётся свой `requestId`, так что
  повторная доставка того же запуска не задваивает сообщение.
- **Чат занят — ничего не теряется**: сообщение встаёт в очередь сессии.
- **В выпадайке настоящие названия чатов** — как в сайдбаре. Список читается из
  проекции, лог сессии только когда проекции нет; результат кешируется, поэтому
  список открывается мгновенно.

### Особенность загрузки плагинов

Плагин намеренно **не импортирует ничего, кроме `node:`** — ни `zod`, ни
пакеты `@deepseek-ai/*`. Плагин, загруженный через симлинк из рабочего
каталога, резолвится в свой реальный путь, откуда пакеты харнесса недоступны
(`ERR_MODULE_NOT_FOUND`). Все возможности харнесса берутся через сервисы
`ctx`, а `defineTool`/`domainTable` заменены их прямыми контрактами. Побочная
выгода — плагин работает и как обычный пакет, без сборки.

## Конфигурация (поле `config` строки патча)

| Поле | По умолчанию | Смысл |
|---|---|---|
| `enabled` | `true` | запускать планировщик; `false` — только панель и инструменты |
| `storePath` | `$DSH_HOME/cron-schedule.json` | файл хранилища |
| `home` | `$DSH_HOME` или `~/.dsh` | каталог для хранилища |
| `locale` | `ru` | язык описаний расписаний (`ru` / `en`) |

## HTTP-маршруты (для панели)

| Метод и путь | Назначение |
|---|---|
| `GET /api/cron-schedule/jobs` | список задач |
| `POST /api/cron-schedule/jobs` | создать задачу |
| `POST /api/cron-schedule/jobs?action=dismiss-missed` | очистить список пропущенных |
| `GET /api/cron-schedule/jobs/<id>` | одна задача |
| `POST /api/cron-schedule/jobs/<id>` | изменить (в том числе `{"enabled": false}`) |
| `POST /api/cron-schedule/jobs/<id>/run` | запустить немедленно; в ответе `lastStatus`, `lastSessionId` (чат этого запуска) и `sessionId` |
| `DELETE /api/cron-schedule/jobs/<id>` | удалить |
| `POST /api/cron-schedule/jobs/preview` | описание и ближайшие запуски выражения |
| `GET /api/cron-schedule/settings` | список допустимых моделей + каталог развёртывания + модель по умолчанию |
| `POST /api/cron-schedule/settings` | задать список допустимых моделей (только человек); значение зеркалится в namespace настроек; `dropped` перечисляет записи, которые развёртывание больше не умеет маршрутизировать и потому не сохранило |
| `GET /api/cron-schedule/chats` | существующие чаты с названиями; `?cwd=<путь>` сужает список до одной папки |
| `GET /api/cron-schedule/manifest` | самоописание плагина одним запросом: инструменты, поля задачи, маршруты с пометкой `humanOnly`, значения `lastStatus` |

## Ограничения

- Задача запускается, только пока работает `dsh web`. Пропущенное за время
  простоя либо догоняется автоматически (если человек поставил галочку
  авто-догона), либо ждёт разрешения в баннере.
- Авто-догон выполняет **один** запуск по факту пропуска, а не по одному на
  каждый пропущенный час: задача должна догнать состояние, а не отработать
  очередь устаревших повторов.
- Время считается по настенным часам пояса задачи. Если local time попадает в
  «дыру» перехода на летнее время, в этот день запуск пропускается — так же
  поступает классический cron.
- Запущенный чат живёт вместе с плагином: перезагрузка плагина (бамп `rev`)
  завершает созданные им сессии.
- Задачи хранят каталог, а не workspace-идентификатор, поэтому задача
  продолжает работать, даже если workspace удалить из списка.
